# Cross-Site Request Forgery (CSRF) Theory

## Overview

Cross-site request forgery (also known as CSRF) is a web security vulnerability that allows an attacker to induce users to perform actions that they do not intend to perform.

![CSRF Concept](Attachments/Pasted%20image%2020260821232712.png)

## Conditions Required for CSRF

For a CSRF attack to be possible, three key conditions must be in place:
- **A relevant action**: There is an action within the application that the attacker has a reason to induce (e.g., modifying permissions or updating email/password).
- **Cookie-based session handling**: Performing the action involves issuing one or more HTTP requests, and the application relies solely on session cookies to identify the user.
- **No unpredictable request parameters**: The requests that perform the action do not contain any parameters whose values cannot be determined or guessed by the attacker.

![CSRF Conditions](Attachments/Pasted%20image%2020260822012713.png)

## CSRF Delivery

- The attacker tricks the victim into visiting a malicious page or link.
- Delivery can happen via **email, social media, or compromised websites**.
- If the vulnerable action uses **GET**, a crafted URL may be enough.

> Since 2021, Chrome enforces `Lax` SameSite restrictions by default.

## CSRF Tokens

A **CSRF token** is a unique, secret, and unpredictable value generated by the server-side application:
- **Unique**
- **Secret**
- **Unpredictable**

The server shares the token with the client, where it can be used to help verify that requests are legitimate.

### CSRF Token Not Tied to the User Session

- Some applications issue CSRF tokens from a **global pool** rather than associating each token with the user’s session.
- The application accepts any token that exists in this pool, regardless of which session received it.

### CSRF Token Tied to a Non-Session Cookie

An attack is possible if an attacker can **set a cookie in the victim’s browser** (e.g., via CRLF injection or cookie tossing).

## SameSite Cookies

### What is a Site in the Context of SameSite Cookies?

![SameSite Definition](Attachments/Pasted%20image%2020260822020249.png)

`http://app.example.com` to `https://app.example.com` is treated as cross-site by most browsers due to different schemes.

![SameSite Scheme Comparison](Attachments/Pasted%20image%2020260822020503.png)

### SameSite Restriction Levels

- `Strict`: Provides strong protection against CSRF by preventing authentication cookies from being sent in cross-site requests.
- `Lax`: Browsers will send the cookie in cross-site requests, but only if both of the following conditions are met:
  - The request uses the `GET` method.
  - The request resulted from a top-level navigation by the user, such as clicking on a link.
- `None`: Disables SameSite restrictions.
- `Secure` attribute: Ensures that the cookie is only sent in encrypted messages over HTTPS.

### Method Override Bypass

Bypassing `Lax` restrictions by overriding the HTTP method with the `_method` parameter in a `GET` request:

```http
GET /my-account/change-email?email=foo%40web-security-academy.net&_method=POST HTTP/1.1
```

### SameSite=Strict Cookie Restriction Bypass

- Cookies with `SameSite=Strict` are **not sent with cross-site requests**.
- This restriction can sometimes be bypassed using a **gadget** that triggers a **secondary request within the same site** (e.g., a client-side redirect).
- Because that secondary request is same-site, the browser includes the `SameSite=Strict` cookie.

## Referer Validation Bypasses

### Validation of Referer Depends on Header Being Present

Craft the CSRF exploit in a way that causes the victim user's browser to drop the `Referer` header:

```html
<meta name="referrer" content="never">
```

### Validation of Referer Can Be Circumvented

If the application merely validates that the Referer contains the target domain name anywhere:

```http
http://attacker-website.com/csrf-attack?vulnerable-website.com
```

This approach may fail in modern browsers that strip query strings from the `Referer` header by default. Override this behavior by ensuring the response containing the exploit has the header:

```http
Referrer-Policy: unsafe-url
```
